# 功法 0 至 13 层完整曲线

## Goal

让所有普通功法从无投入的 0 层开始，并通过一条完整的 0 至 13 层整数曲线成长。
新增的 0 至 1 层成本必须等于原 1 至 2 层成本；原有 1 至 13 层每段成本、玩家境界
经验及其他平衡数值不变，功法满层容量随新增的一段自然增加。

## Requirements

* `invested_amount = 0` 必须推导为功法 0 层；达到第 1 层必须投入完整的入门段成本。
* 以旧 12 段曲线 `old = (c1, c2, ..., c12)` 为基准，新 13 段曲线必须为
  `(c1, c1, c2, ..., c12)`。
* 新曲线每段必须为正整数，新 `max_investment` 必须等于旧容量加 `c1`；不能为了锁死
  旧容量而压缩、拆分或重新归一化后续成本。
* 原有 1 至 13 层的每段增量成本保持不变。新增段会让新层数的累计阈值整体增加
  `c1`，这是明确接受的结果。
* 练气普通功法的旧成本为 `(15, 22, ..., 1265)`，新成本必须以
  `(15, 15, 22, ..., 1265)` 开始，单门容量从 3,765 增至 3,780，三门满层总量从
  11,295 增至 11,340。三门总量只需不少于练气十层门槛 11,293，无需精确贴合。
* 后续境界同理：原本按“至少三门满层覆盖对应境界门槛”得到的基础容量可以有余量，
  新增入门段不要求反向修改境界门槛。
* `current_layer` 仍是在每次投入变更事务中由权威 `invested_amount` 推导并同步写入的
  查询投影，不能由调用方自行维护。
* PostgreSQL 的开发期 migration 直接写成最终结构：`current_layer` 范围为 0 至 13、
  默认值为 0，功法目录和测试数据直接使用扩展后的 `max_investment`。不新增兼容 revision、
  旧曲线回填、降级保护或运行时兜底。
* Game Service API 形状保持不变，只允许 `current_layer` 返回 0；功法升级任务目标仍为
  绝对层数 1 至 13，0 层不作为有意义的任务目标。
* Paper DTO 接受 0 至 13；功法 GUI 自然展示 `0/13`，仍以权威投入量与层数为准。
* 公共 Wiki 使用简体中文，说明 0 层语义、最终曲线规则和任务目标边界。
* 普通闭关改为 10 秒一个离散炼化周期。10/20/50/100 小时满层时间仅用于推导单位
  时间基础速度，不再作为玩家必须等待的闭关完成时间。
* 每个功法组（`qi` 或 `level:14..22`）有固定的 10 秒基础炼化量：以该组功法容量和
  对应大境界的原满层估算时间计算，使用整数向下取整且最低为 1。
* 一次闭关选择的功法必须属于同一 `group_code` 且使用相同满层容量，使一个会话只有
  一套明确的小境界基础速度；原有 1 至 5 门、平均分配和容量溢出再分配规则保持不变。
* 玩家修炼较低大境界功法时，速度倍率使用寿命权重比
  `player_speed_weight / technique_speed_weight`，权重为练气/筑基/结丹/元婴
  `1/2/5/10`。同大境界倍率为 1，例如筑基炼练气为 2 倍、元婴炼筑基为 5 倍、
  元婴炼结丹为 2 倍速度。该倍率不修改功法容量、层数成本或修为价值。
* `3:2`、`17:10`、`9:5`、`2:1` 仅是 0 至 13 层成本曲线的段间增长比，绝不参与
  闭关速度计算。
* 区域 `speed_basis_points` 继续乘在每周期速度上，`yield_basis_points` 继续控制消耗
  储备与实际保留投入的换算。最终每周期量在会话开始时向下取整为正整数并冻结。
* `completes_at` 对普通闭关表示首次可结算周期，而不是预计满层时刻；Paper 开始后及
  每次仍为 active 的结算后都按 10 秒调度下一次结算，不再等待数小时或固定重试 60 秒。
* Game Service 使用完整 10 秒周期累计生成量；不足 10 秒不产出，延迟或离线后的多个
  完整周期可一次追赶，重复/分段结算必须与一次合并结算相同。
* 当前仍处于可丢弃数据的开发阶段。模型改变后删除本地 PostgreSQL volume 并从空库
  建立最终结构；旧功法行和旧开放闭关会话不迁移、不回填、不读取。

## Technical Approach

先按原算法生成冻结的 12 段几何曲线，再把原第一段完整复制到曲线最前方。新容量为
旧容量加原第一段成本；层数推导从 0 开始扫描 13 段成本。运行时对扩展后容量使用带
重复首权重的 13 段分配，并以精确测试锁定所有正式容量都重现
`(c1, c1, c2, ..., c12)`。

直接重写开发期 schema revision 与 ORM：功法层数从 0 开始，普通闭关会话冻结 10 秒周期、
功法组、基础量、玩家/功法速度权重、区域倍率和最终每周期量。运行时累计公式只读取最终
快照，Paper 每 10 秒触发一次权威结算。实现完成后删除本地数据库并从空库升级到 head。

## Decision (ADR-lite)

**Context**: 把 0 层仅作为显示别名会让少量正投入直接获得第 1 层；为了保持旧总容量
而拆分第一段，又会让 0 至 1 层显著低于原来的入门成本。

**Decision**: 完整复制旧第一段作为 0 至 1 层成本，允许功法满层容量随之增加。

**Consequences**: 新的前两段成本相同，原有每段成本和玩家境界阈值不变；功法满层容量
和相同闭关时间内的最大可保留修为略有增加。练气三门满层比练气十层门槛多 47 点，
符合“至少覆盖”的原始平衡目标。本地开发数据直接删除，由最终目录重新创建。

## Out of Scope

* 不修改玩家 1 至 22 级境界目录、任何 `max_exp` 或突破规则。
* 不修改功法效果数值、最高层数或满层耗时；只按新增第一段扩展容量。
* 不增加 0 层任务目标、功法学习流程或新的功法内容。
* 不在 Paper 本地计算或保存可信炼化量；10 秒调度只是调用权威结算接口。
